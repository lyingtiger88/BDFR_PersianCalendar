# زروان — Handoff اجرای سریع برای آماده‌سازی انتشار

**هدف:** رساندن نسخه Windows و Android زروان به یک نسخه پایدار و قابل عرضه، در کوتاه‌ترین زمان واقع‌بینانه. این سند نقطه شروع کار ایجنت توسعه است.

**وضعیت تصمیم‌ها**
- دامنه انتشار فعلی: فقط Windows و Android؛ iOS فعلاً خارج از دامنه نسخه 1.0 است.
- اولویت با تثبیت قابلیت‌های موجود و رفع باگ‌هاست، نه افزودن قابلیت جدید.
- طراحی کلی رابط کاربری مورد تأیید صاحب پروژه است. بازطراحی UI انجام نشود؛ فقط ایرادهای واقعی روانی استفاده و UX که در کد/گزارش‌ها قابل اثبات‌اند اصلاح شوند. صاحب پروژه در حال کار روی روانی استفاده است؛ تغییرات او را بدون هماهنگی overwrite نکنید.
- قابلیت‌های پومودورو، گروه‌های ابری و همگام‌سازی ابری کامل، قابلیت‌های جدید این انتشار نیستند. قابلیت ناقص را آماده یا قابل فروش معرفی نکنید.
- هیچ تاریخ انتشار قطعی را تضمین نکنید. هدف «هرچه زودتر، بدون قربانی کردن صحت تقویم و سلامت داده» است.

## ترتیب اجرای اجباری

### P0 — صحت تقویم و باگ‌های مسدودکننده
1. کد و تست‌های فعلی تاریخ شمسی، میلادی و قمری را بررسی کنید؛ منطق موجود را قبل از تغییر مستند کنید.
2. موارد ثبت‌شده در issue شماره 1 را بررسی کنید: نام کامل روزهای هفته، RTL/LTR، تعطیلی اشتباه، اختلاف یک‌روزه تاریخ قمری و نمایش ماه‌های هم‌پوشان.
3. تعطیلات و مناسبت‌ها را با منبع معتبر/رسمی و برای تمام سال‌های پشتیبانی‌شده تطبیق دهید.
4. برای هر اصلاح، تست رگرسیون اضافه کنید. از اصلاح حدسی تاریخ‌ها خودداری کنید.

### P0 — سلامت داده و انتشار
5. مسیرهای backup/restore و مهاجرت دیتابیس را پیدا و روی داده نمونه و داده موجود آزمایش کنید؛ بازیابی باید بدون حذف یا تکراری‌شدن داده انجام شود.
6. نصب تمیز، ارتقا از نسخه قبلی و حفظ داده کاربر را در Windows و Android آزمایش کنید.
7. Android: خروجی Release امضاشده (APK و در صورت نیاز AAB) بسازید؛ کلید امضا فقط از GitHub Secrets/محیط امن خوانده شود و هرگز در مخزن commit نشود.
8. Windows: Setup و portable را بررسی کنید؛ نسخه، شناسه build، مسیر داده کاربر، نصب/ارتقا/حذف و امضای Authenticode یا تصمیم مستند برای انتشار بدون امضا را مشخص کنید.
9. فعال‌سازی لایسنس را برای نصب تازه، دستگاه جدید، حالت آفلاین، انقضا و کلید عمومی تولید تست کنید. کلید خصوصی یا secret را وارد مخزن نکنید.
10. مجوزها، داده‌های جمع‌آوری‌شده، نگهداری/حذف داده و متن سیاست حریم خصوصی را بررسی کنید.
11. خطاهای crash، لاگ و سناریوهای پرتکرار را بررسی کنید.

### P1 — پس از عبور از P0 یا در صورت نبود مانع انتشار
12. مستندات نصب و راهنمای کوتاه کاربر، release notes و checksum بسته‌ها را آماده کنید.
13. دسترس‌پذیری و بهبودهای ظاهری را فقط در حد باگ یا مانع استفاده اصلاح کنید.

## قواعد کار ایجنت
- قبل از هر تغییر، ساختار پروژه، وضعیت branch و تغییرات محلی/اخیر را بررسی کنید.
- تغییرات صاحب پروژه را overwrite یا revert نکنید.
- کار را به بسته‌های کوچک و قابل بازبینی تقسیم کنید؛ هر بسته باید build و تست مرتبط داشته باشد.
- از تغییرات گسترده معماری، بازنویسی غیرضروری یا افزودن dependency بدون دلیل خودداری کنید.
- هیچ تستی را صرفاً برای سبز شدن CI حذف یا بی‌اثر نکنید.
- اگر تست واقعی به دستگاه/کلید/سرویس بیرونی نیاز دارد و در دسترس نیست، آن را صریحاً «اجرا نشده» گزارش کنید؛ موفقیت فرضی ثبت نکنید.
- برای هر باگ: شرح، علت ریشه‌ای، فایل‌های تغییرکرده، تست اضافه/اجراشده و نتیجه را گزارش کنید.
- تغییرات را در branch جداگانه انجام دهید و از طریق Pull Request ارائه کنید؛ تا زمان بازبینی، مستقیم روی main ادغام نکنید.
- پس از هر مجموعه تغییر، این handoff را با وضعیت جدید، تصمیم‌ها و موارد باز به‌روزرسانی کنید.

## معیار پذیرش نسخه اولیه
- تمام موارد P0 در issue شماره 1 بسته شده باشند یا با دلیل روشن و تأیید صاحب پروژه از دامنه انتشار خارج شده باشند.
- CI روی commit نهایی Windows و Android موفق باشد.
- نصب تمیز، ارتقا، حفظ داده و backup/restore روی محیط واقعی تأیید شده باشد.
- محاسبات تقویم و مناسبت‌ها دارای تست رگرسیون و تطبیق مستند باشند.
- نسخه انتشار Android امضاشده و بسته Windows قابل نصب/استفاده آماده باشد.
- هیچ قابلیت ناقصی در صفحه معرفی یا توضیحات انتشار به‌عنوان آماده عرضه معرفی نشود.

## گزارش مورد انتظار از ایجنت در شروع
1. فهرست دقیق پروژه‌ها/ماژول‌های Windows و Android و دستور build هرکدام.
2. آخرین وضعیت CI و تست‌ها، با لینک run یا شواهد.
3. نگاشت هر مورد P0 به فایل/ماژول و وضعیت فعلی آن.
4. موانع واقعی که برای رفعشان به تصمیم یا دسترسی صاحب پروژه نیاز است.
5. اولین بسته تغییر پیشنهادی با تخمین کوتاه و معیار پذیرش.

**مرجع برنامه انتشار:** issue شماره 1 در GitHub با عنوان «Zurvan 1.0 — Android + Windows simultaneous release readiness».
